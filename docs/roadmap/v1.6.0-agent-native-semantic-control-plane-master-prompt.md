# SotuRail v1.6.0 — Agent-Native Semantic Control Plane — Master Implementation Prompt

Use this prompt with a coding agent that has access to the SotuRail repository.

## Mission

Implement the next SotuRail release as **v1.6.0 — Agent-Native Semantic Control Plane**.

The release must make SotuRail easy for capable AI agents to discover, understand and use directly through portable Agent Skills and self-describing capabilities, while preserving the v1.5 trust core.

The design rule is:

```text
AI understands.
SotuRail organizes, constrains and proves.
```

And:

```text
Do not hardcode intelligence that the agent can perform better.
Do not delegate truth that deterministic systems can prove better.
```

Do not treat this prompt as proof of repository state. Audit the real repository first.

---

## 0. Operating mode

Work incrementally.

Use the user's preferred engineering loop:

```text
targeted local validation
-> logical commit
-> push
-> CI runs asynchronously
-> continue independent work
-> check CI between tasks
```

Rules:

- do not wait idly for CI when independent work remains;
- do not rerun the full suite after every small change;
- run focused tests for the touched subsystem;
- fix red CI early before stacking unrelated work;
- use full/release gates at milestones and before release;
- preserve a last-known-green SHA;
- never weaken tests/security merely to go faster;
- avoid giant commits and meaningless microcommits.

Before the release tag, the exact release SHA on `main` must have all required checks green.

## 4. Agent Skills standards and progressive disclosure

Implement against the verified common Agent Skills model, not a SotuRail-only private convention.

Minimum portable structure:

```text
<skill>/
  SKILL.md
  references/   optional
  scripts/      optional
  assets/       optional
```

`SKILL.md` must contain concise discovery metadata and workflow instructions.

Use progressive disclosure:

### Level 1 — discovery

Only enough metadata for the agent to decide relevance:

- stable skill name;
- concise description;
- when to use;
- when not to use;
- optional scope/path metadata where the host supports it.

### Level 2 — selected skill

Load the workflow:

- task goal;
- required inputs;
- SotuRail capability IDs;
- decision/clarification guidance;
- safety constraints;
- expected structured artifacts;
- completion/verification rules.

### Level 3 — on-demand resources

Load only when necessary:

- references;
- schemas;
- examples;
- templates;
- scripts;
- provider notes.

Do not put the complete SotuRail manual into every `SKILL.md`.

Keep skill discovery metadata small. Large skill catalogs are a context-budget risk.

## 5. Portable SotuRail Core Skill

Create a first-class portable Core Skill.

Purpose:

```text
Teach an agent that SotuRail is available and how to use it without
requiring the agent to memorize the CLI.
```

The Core Skill should teach:

```text
discover -> select -> act -> verify
```

It should tell the agent to:

1. understand the user's task;
2. discover relevant SotuRail capabilities/skills;
3. load only what is necessary;
4. use SotuRail/provider/project sources;
5. return structured candidate artifacts;
6. preserve source/provenance;
7. collect/verify evidence where required;
8. respect freshness, authority and readiness;
9. ask the user only for real decisions/ambiguities that cannot be resolved from evidence.

It must explicitly say that model confidence is not verification.

## 7. Capability Descriptor v2

Evolve the v1 Capability Registry compatibly.

Do not delete v1 fields without migration.

Add a v2 descriptor or additive schema capable of expressing:

- stable `id`;
- stable semantic key;
- maturity/version;
- purpose;
- inputs;
- outputs/artifact schemas;
- surfaces:
  - skill;
  - MCP;
  - CLI;
  - SDK/artifact where applicable;
- permissions;
- side effects;
- approval requirement;
- evidence requirement;
- freshness requirement;
- provider class;
- provider candidates/availability;
- fallback behavior;
- localization/language capability;
- docs;
- trust state allowed from an agent/provider result.

Example concept:

```yaml
id: structural.impact
schemaVersion: soturail.capability.v2
purpose:
  semanticKey: structural_impact
outputs:
  artifact: soturail.impact.v1
surfaces:
  skill: true
  mcp: true
  cli: true
trust:
  provenanceRequired: true
  freshnessRequired: true
  agentResultState: candidate
localization:
  machineSemantics: locale-independent
  preserveSource: true
```

The descriptor is the source of truth from which host/skill surfaces can be generated or validated.

## 8. Capability discovery

Agents must be able to discover SotuRail without reading the full docs.

Provide a small machine-readable discovery surface.

It may be exposed through existing MCP/CLI/artifacts, but avoid duplicate truth.

Required conceptual operations:

```text

list relevant skills
describe skill

```

If CLI commands are added, keep them thin projections of the registry.

If MCP resources/tools are added, keep them typed and bounded.

## 9. Semantic Worker contract

Formalize the external AI agent as a **Semantic Worker**.

The worker receives:

- user task;
- workspace/run identity;
- selected context or references;
- active contract;
- available skills/capabilities;
- policy constraints;
- evidence requirements;
- expected output schema.

The worker may perform:

- natural-language interpretation;
- requirement understanding;
- semantic classification;
- project/domain vocabulary resolution;
- ambiguity detection;
- questions;
- synthesis;
- candidate impact analysis;
- candidate claims;
- candidate decisions;
- capability selection;
- provider result interpretation.

The worker must not be able to create trusted states by assertion.

Output states include:

- `candidate`;
- `inferred`;
- `assumed`;
- `unknown`;
- `unverified`.

Promotion to stronger states requires SotuRail evidence rules.

## 10. Structured candidate artifacts

Add minimal, versioned schemas for semantic worker outputs.

At minimum consider:

- candidate claim;
- candidate impact;
- candidate decision;
- unresolved question;
- interpretation/synthesis record.

Each candidate should preserve:

- original statement/text when sourced;
- source refs;
- workspace/run binding when applicable;
- confidence as model metadata, not proof;
- locale if known;
- producer/host;
- timestamp;
- verification state;
- dependencies.

Do not store chain-of-thought. Store concise rationale/evidence references needed for engineering traceability.

## 11. Language-neutral machine semantics

This is a P0 v1.6 requirement.

The system must work when:

- user speaks Portuguese;
- code identifiers are English;
- docs are mixed Portuguese/English;
- requirements are Spanish;
- filenames contain accents;
- a Japanese project uses Japanese docs/paths;
- a provider returns English documentation;
- the agent answers in another user-preferred language.

Rules:

1. capability IDs, artifact types, enums and protocol values are locale-independent;
2. human-facing descriptions may be localized;
3. original source text is preserved;
4. translation is a derived view and never silently replaces evidence;
5. code symbols, exact paths and commands stay exact;
6. Unicode paths are first-class;
7. unknown/mixed locale is valid;
8. no mandatory translation step in the deterministic critical path;
9. semantic providers must declare language limitations/capabilities when relevant.

Do not implement one keyword list per language.

## 12. Remove semantic authority from keyword heuristics

Inspect current routing/search/rules code.

Known v1.5 example:

`src/core/skill-routing.ts` uses keyword scoring over task text and skill text.

Do not simply delete compatibility behavior.

Change architecture so:

- capable agent skill selection is primary;
- keyword routing is fallback/diagnostic/baseline only;
- fallback results are labeled as heuristic;
- heuristic output cannot satisfy verification/readiness;
- host skill discovery uses standard name/description metadata;
- tests prove non-English tasks do not depend on English keyword tables.

Apply the same principle to other natural-language heuristics found during audit.

Classify every current parser/heuristic as one of:

```text
KEEP_AS_PROOF
KEEP_AS_STRUCTURAL_FACT
KEEP_AS_FALLBACK
REPLACE_WITH_STRUCTURED_SIGNAL
DELEGATE_TO_SEMANTIC_WORKER
DEPRECATE
```

Document the result.

## 13. Do not remove legitimate deterministic parsers

- compiler/typechecker output;
- JUnit/structured test output;
- lockfiles;
- protocol messages;
- exact tool status/exit codes.

Do not turn objective signals into model guesses.

The goal is not "LLM everything."

## 16. MCP + Skill relationship

Maintain this distinction:

```text
MCP = capability/tool/resource boundary
Skill = procedure that teaches the model how to compose capabilities
```

A Skill may instruct an agent to call SotuRail MCP tools/resources.

Do not make the Skill duplicate MCP logic.

Do not expose arbitrary shell merely to make Skills convenient.

## 20. Security requirements

Skills are instructions, not authority.

Threat model:

- malicious/unreviewed skill;
- prompt injection in project docs;
- skill asking for secrets;
- provider returning malicious instructions;
- skill requesting broad MCP exposure;
- agent claiming it verified something it did not execute;
- host-specific export changing permissions unexpectedly.

Required behavior:

- least privilege;
- explicit side-effect metadata;
- human approval for high-consequence external writes;
- raw logs redacted by default;
- no secret in exported skill/context files;
- WorkspaceGuard on project reads;
- capability policy before action;
- provenance on provider/semantic outputs;
- candidate vs verified state enforcement.

## 26. Acceptance criteria

v1.6 cannot be considered complete unless all are true:

1. A capable supported agent can discover SotuRail Skills without memorizing CLI commands.
2. Core Skill uses progressive disclosure.
3. At least the initial task-skill set is capability-backed, not duplicate logic.
4. Capability Descriptor v2 is machine-readable and backward-compatible or migratable.
5. Agent output cannot self-promote to verified/current/approved/ready.
6. Keyword routing is no longer the primary semantic authority.
7. Non-English tasks work without per-language keyword lists.
8. Original source language is preserved.
9. Unicode path fixtures pass.
10. Host adapters are explicitly tested; unknown hosts use generic fallback.
11. MCP remains bounded; Skills do not gain arbitrary shell authority.
12. v1.5 trust/security/freshness contracts do not regress.
13. Docs accurately separate shipped/planned/experimental features.
14. Skill/task evals measure correctness, not only token/output size.
15. Full release SHA is green before tag/release.
