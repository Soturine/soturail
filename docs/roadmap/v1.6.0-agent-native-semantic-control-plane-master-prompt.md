# SotuRail v1.6.0 — Agent-Native Semantic Control Plane — Master Implementation Prompt

Use this prompt with a coding agent that has access to the SotuRail repository.

## Mission

Implement the next SotuRail release as **v1.6.0 — Agent-Native Semantic Control Plane**.

The release must make SotuRail easy for capable AI agents to discover, understand and use directly through portable Agent Skills and self-describing capabilities, while preserving the v1.5 trust core.

The design rule is:

```text
AI understands.
SotuRail organizes, constrains and proves.
```

And:

```text
Do not hardcode intelligence that the agent can perform better.
Do not delegate truth that deterministic systems can prove better.
```

Do not treat this prompt as proof of repository state. Audit the real repository first.

---

## 0. Operating mode

Work incrementally.

Use the user's preferred engineering loop:

```text
targeted local validation
-> logical commit
-> push
-> CI runs asynchronously
-> continue independent work
-> check CI between tasks
```

Rules:

- do not wait idly for CI when independent work remains;
- do not rerun the full suite after every small change;
- run focused tests for the touched subsystem;
- fix red CI early before stacking unrelated work;
- use full/release gates at milestones and before release;
- preserve a last-known-green SHA;
- never weaken tests/security merely to go faster;
- avoid giant commits and meaningless microcommits.

Before the release tag, the exact release SHA on `main` must have all required checks green.

---


## 0.1. Git authorship and attribution — mandatory

Use the repository owner's existing Git identity for every commit.

Mandatory rules:

- **Do not add Claude as contributor or co-author.**
- Do not add `Co-authored-by: Claude ...`, `Co-authored-by: Anthropic ...`, bot attribution, AI attribution, "Generated by Claude", "Assisted by Claude", or similar trailers/messages.
- Do not change `git config user.name` or `git config user.email` to an AI/bot identity.
- Do not add Claude/Anthropic to AUTHORS, CONTRIBUTORS, package metadata, release notes or repository credits unless the human owner explicitly requests it later.
- Commit messages must describe the engineering change, not the model/tool that produced it.
- Do not rewrite existing history merely to change authorship.

Technical provenance fields may still record a runtime/provider/model when that is genuinely part of SotuRail's product evidence model. That is different from Git authorship or repository credit.

## 0.2. Commit, push and checkpoint discipline — mandatory

Work directly on `main` unless a repository protection rule makes that impossible.

Do not accumulate the whole release into one giant local commit.

For each logical checkpoint:

```text
implement one coherent slice
-> run targeted validation for that slice
-> commit with the owner's normal Git identity
-> push to main immediately
-> CI starts asynchronously
-> record checkpoint status
-> continue independent next work when safe
-> inspect CI before the next risky/significant push
```

Rules:

- every logical implementation slice gets its own meaningful commit;
- push each logical commit to `main`;
- do not wait idly for CI if the next task is independent;
- do not stack unrelated work on a known-red `main`;
- if CI fails, inspect the exact failed job and fix it early;
- keep a `last-known-green` SHA in the implementation log/checkpoint notes;
- avoid rerunning full suites locally when the same SHA already has equivalent green evidence;
- use focused tests during development;
- run heavy/full release validation only at milestone boundaries or when blast radius justifies it;
- docs must be updated in the same checkpoint as the behavior they describe;
- do not create a release tag until the exact intended release SHA on `main` is green.

Each checkpoint report should record:

```text
checkpoint
scope
files/modules changed
targeted tests
commit SHA
push status
CI status
last-known-green
remaining blockers
```

Suggested checkpoint/commit sequence appears later in this prompt. Adjust only when the real repository dependency graph justifies it.

## 3.1. Semantic-first automation — mandatory interpretation

The central change in v1.6 is **not** "delete determinism" and it is **not** "LLM everything".

It is:

> Stop using hardcoded parsers, keyword heuristics and language/stack-specific rules as the primary source of semantic intelligence. Let the capable AI agent do natural-language/project semantic work through SotuRail Skills and capabilities. Keep deterministic code where objective facts and trust can actually be proven.

The responsibility split is:

```text
Natural-language meaning / intent / project semantics / ambiguity / synthesis
    -> AI agent / Semantic Worker

Objective machine-observable facts / proof / trust transitions
    -> deterministic SotuRail core

Specialized optional capability
    -> provider

Procedure, discovery and composition guidance
    -> Skill
```

### Semantic work that should normally move to the AI agent

- understand the user's natural-language request;
- infer task intent from project context;
- interpret requirements and domain language;
- identify candidate business rules;
- relate docs/code/tests/configs conceptually;
- detect ambiguity/conflict;
- decide which SotuRail Skills/capabilities are relevant;
- select context based on task meaning;
- synthesize provider/tool outputs;
- propose impact, claims, questions and decisions;
- summarize evidence for the human;
- work across languages without requiring per-language keyword tables.

### Deterministic work that remains authoritative

- filesystem containment and WorkspaceGuard;
- paths and canonicalization;
- Git HEAD/dirty/staged/untracked state;
- hashes/fingerprints/digests;
- artifact storage/recovery;
- JSON/YAML/protocol/schema parsing;
- lockfiles/package manifests;
- AST/LSP/compiler facts;
- JUnit/structured test reports;
- exit/status/error codes;
- CI/job status;
- permissions and policy;
- provenance and freshness;
- authority/readiness state transitions;
- exact-digest Execution Envelope checks.

### Patterns to stop treating as architecture

Do not expand these as the semantic core:

- English keyword routers;
- lists of synonyms for every language;
- regexes that infer business meaning;
- one business-rule parser per framework/domain;
- one router per stack;
- hardcoded assumptions that tests use words like `should`;
- hardcoded assumptions that failures contain `error` or `failed`;
- fixed host enums spread throughout unrelated modules;
- forcing every agent to memorize SotuRail CLI commands;
- reimplementing semantic reasoning already available in the active coding agent.

Existing heuristics may temporarily remain as compatibility, offline fallback, diagnostics or benchmark baselines. Their output must be clearly labeled heuristic/candidate and cannot satisfy verification/readiness by itself.

### Normal automated agent experience

For a capable agent, the default experience should become:

```text
user asks in natural language
-> host discovers SotuRail Core Skill
-> agent loads only relevant Skill metadata/instructions
-> agent chooses capabilities from task semantics
-> SotuRail resolves native/provider capability implementations
-> agent gathers only needed context
-> agent interprets project meaning
-> agent emits structured candidate artifacts
-> SotuRail checks provenance/freshness/policy/evidence
-> agent continues implementation/review/release
```

The user should not need to translate their request into CLI commands.

The agent should not need to ask "which SotuRail command should I run?" for ordinary supported workflows.

CLI remains available for humans, CI, administration, debugging, recovery and deterministic automation.

## 4. Agent Skills standards and progressive disclosure

Implement against the verified common Agent Skills model, not a SotuRail-only private convention.

Minimum portable structure:

```text
<skill>/
  SKILL.md
  references/   optional
  scripts/      optional
  assets/       optional
```

`SKILL.md` must contain concise discovery metadata and workflow instructions.

Use progressive disclosure:

### Level 1 — discovery

Only enough metadata for the agent to decide relevance:

- stable skill name;
- concise description;
- when to use;
- when not to use;
- optional scope/path metadata where the host supports it.

### Level 2 — selected skill

Load the workflow:

- task goal;
- required inputs;
- SotuRail capability IDs;
- decision/clarification guidance;
- safety constraints;
- expected structured artifacts;
- completion/verification rules.

### Level 3 — on-demand resources

Load only when necessary:

- references;
- schemas;
- examples;
- templates;
- scripts;
- provider notes.

Do not put the complete SotuRail manual into every `SKILL.md`.

Keep skill discovery metadata small. Large skill catalogs are a context-budget risk.

## 4.1. Skill architecture principles gathered from the benchmark/research work

Use the lessons from the reviewed skill ecosystems and agent harnesses.

### Progressive disclosure

Do not eagerly load the whole skill catalog or full documentation.

Prefer:

```text
Level 1: name + concise description
        -> agent decides relevance

Level 2: selected SKILL.md
        -> workflow, capabilities, constraints

Level 3: references/scripts/assets
        -> loaded only if needed
```

### Skill is procedure, not duplicated engine code

A Skill should explain:

- when it applies;
- which canonical capabilities it can use;
- which evidence/trust constraints apply;
- how to finish/verify the task.

It should not contain a second implementation of the capability.

### Small, composable catalog

Do not create hundreds of always-visible skills.

Start with a small high-value set and evaluate them.

Multiple skills may compose for one task, for example:

```text
"Fix OAuth login regression"

soturail-core
+ soturail-change
+ soturail-debug
+ soturail-security
```

The agent chooses/composes them based on semantic task understanding.

### Host portability

Do not assume "Skill" means only one vendor directory.

The canonical Skill is portable. Host adapters may project it to the native representation each verified host supports.

Unknown/unverified hosts use the generic portable fallback.

### Skill discovery must be easy for agents

An agent entering a SotuRail-enabled repository should be able to answer:

- What is SotuRail?
- What can it do?
- Which Skills are available?
- Which capabilities does this Skill use?
- What is safe/unsafe?
- Which evidence is required?
- Which provider is available?
- What is stale/unavailable?

without reading the entire repository or memorizing CLI syntax.

## 5. Portable SotuRail Core Skill

Create a first-class portable Core Skill.

Purpose:

```text
Teach an agent that SotuRail is available and how to use it without
requiring the agent to memorize the CLI.
```

The Core Skill should teach:

```text
discover -> select -> act -> verify
```

It should tell the agent to:

1. understand the user's task;
2. discover relevant SotuRail capabilities/skills;
3. load only what is necessary;
4. use SotuRail/provider/project sources;
5. return structured candidate artifacts;
6. preserve source/provenance;
7. collect/verify evidence where required;
8. respect freshness, authority and readiness;
9. ask the user only for real decisions/ambiguities that cannot be resolved from evidence.

It must explicitly say that model confidence is not verification.

## 11. Language-neutral machine semantics

This is a P0 v1.6 requirement.

The system must work when:

- user speaks Portuguese;
- code identifiers are English;
- docs are mixed Portuguese/English;
- requirements are Spanish;
- filenames contain accents;
- a Japanese project uses Japanese docs/paths;
- a provider returns English documentation;
- the agent answers in another user-preferred language.

Rules:

1. capability IDs, artifact types, enums and protocol values are locale-independent;
2. human-facing descriptions may be localized;
3. original source text is preserved;
4. translation is a derived view and never silently replaces evidence;
5. code symbols, exact paths and commands stay exact;
6. Unicode paths are first-class;
7. unknown/mixed locale is valid;
8. no mandatory translation step in the deterministic critical path;
9. semantic providers must declare language limitations/capabilities when relevant.

Do not implement one keyword list per language.

## 11.1. Any user, any project, any language — explicit requirement

SotuRail must not be architected around English-speaking users or English-only repositories.

Support the general case:

```text
user language != project docs language != code identifier language != provider language
```

Examples that must remain valid:

- user asks in Portuguese, code and libraries are English;
- user asks in Japanese, requirements are Japanese, identifiers are English;
- docs contain Portuguese + English simultaneously;
- Spanish requirement references an English API;
- project paths contain accents, CJK characters or other Unicode;
- provider returns English docs, but the user's preferred output is another language.

Keep machine identity separate from presentation:

```text
canonical id: structural.impact

pt-BR display: Análise de impacto estrutural
en-US display: Structural impact analysis
es display: Análisis de impacto estructural
ja display: localized presentation

same capability identity in every case
```

Never localize exact:

- source code identifiers;
- filesystem paths;
- command names/arguments;
- hashes/digests;
- artifact IDs;
- protocol enums.

Preserve original source text in evidence. A translation/localized explanation is derived data.

Do not solve multilingual support by adding a giant multilingual synonym dictionary.

Use the active Semantic Worker for natural-language meaning; use deterministic structures for machine contracts.

## 12. Remove semantic authority from keyword heuristics

Inspect current routing/search/rules code.

Known v1.5 example:

`src/core/skill-routing.ts` uses keyword scoring over task text and skill text.

Do not simply delete compatibility behavior.

Change architecture so:

- capable agent skill selection is primary;
- keyword routing is fallback/diagnostic/baseline only;
- fallback results are labeled as heuristic;
- heuristic output cannot satisfy verification/readiness;
- host skill discovery uses standard name/description metadata;
- tests prove non-English tasks do not depend on English keyword tables.

Apply the same principle to other natural-language heuristics found during audit.

Classify every current parser/heuristic as one of:

```text
KEEP_AS_PROOF
KEEP_AS_STRUCTURAL_FACT
KEEP_AS_FALLBACK
REPLACE_WITH_STRUCTURED_SIGNAL
DELEGATE_TO_SEMANTIC_WORKER
DEPRECATE
```

Document the result.

## 20. Security requirements

Skills are instructions, not authority.

Threat model:

- malicious/unreviewed skill;
- prompt injection in project docs;
- skill asking for secrets;
- provider returning malicious instructions;
- skill requesting broad MCP exposure;
- agent claiming it verified something it did not execute;
- host-specific export changing permissions unexpectedly.

Required behavior:

- least privilege;
- explicit side-effect metadata;
- human approval for high-consequence external writes;
- raw logs redacted by default;
- no secret in exported skill/context files;
- WorkspaceGuard on project reads;
- capability policy before action;
- provenance on provider/semantic outputs;
- candidate vs verified state enforcement.

## 26. Acceptance criteria

v1.6 cannot be considered complete unless all are true:

1. A capable supported agent can discover SotuRail Skills without memorizing CLI commands.
2. Core Skill uses progressive disclosure.
3. At least the initial task-skill set is capability-backed, not duplicate logic.
4. Capability Descriptor v2 is machine-readable and backward-compatible or migratable.
5. Agent output cannot self-promote to verified/current/approved/ready.
6. Keyword routing is no longer the primary semantic authority.
7. Non-English tasks work without per-language keyword lists.
8. Original source language is preserved.
9. Unicode path fixtures pass.
10. Host adapters are explicitly tested; unknown hosts use generic fallback.
11. MCP remains bounded; Skills do not gain arbitrary shell authority.
12. v1.5 trust/security/freshness contracts do not regress.
13. Docs accurately separate shipped/planned/experimental features.
14. Skill/task evals measure correctness, not only token/output size.
15. Full release SHA is green before tag/release.
