# v1.7 Real-Agent Qualification Results (Checkpoints 1–4)

Date: 2026-10-18

Plan and promotion criteria: [v1.7 Real-Agent Qualification Baseline](v1.7.0-real-agent-qualification-baseline.md). Harness, tasks and raw records: [`benchmarks/agent-qualification/`](../../benchmarks/agent-qualification/README.md).

Evidence states used below: **verified** = reproduced by a deterministic check or an oracle with controls; **observed** = seen in agent runs, n too small to generalize; **documented** = described in docs, not exercised.

## 1. Answer in one paragraph

On 12 small, oracle-scored engineering tasks, SotuRail 1.6.0 did **not** improve task correctness for any agent tested. Claude Code (Sonnet 5.5, Haiku 5.5) almost never used it even when its Skills and MCP server were installed, and paid 8–24% more per run for the extra context; an apparent Haiku gain in one repetition did not reproduce in three. Codex used it on every run, at 2.5–3.1× the tokens and 2–2.5× the wall time, and the published 1.6.0 made it **worse**: a fingerprint defect marked the agent's own fresh evidence stale, so 42% of correct Codex results were reported NOT_READY. That defect and three others found by dogfooding are fixed on `main`; with the fix, stale-evidence false-not-ready went from 5/12 to 0/12, and scaling the skills' ceremony to the task cut Codex's SotuRail tokens by about a fifth — still about 2.2× the baseline. What SotuRail demonstrably adds today is the deterministic layer — guarded paths, freshness binding, caller claims that cannot satisfy readiness — not better agent outcomes on small tasks.

## 2. Evaluation set-up (Checkpoint 1)

- 12 tasks: bug ×2, debug, feature ×2, refactor, review, security ×2, requirements, documentation, release; Node and Python; prompts in en, pt-BR, es, ja.
- Arms: `baseline`, `skills` (documented quickstart with the published package), `skills-mcp`. Identical prompt (never mentions SotuRail), model, limits and permission mode.
- Oracles: hidden tests/structural checks copied in after the agent exits. Every oracle passes a negative control (fails the untouched fixture), a positive control (passes a reference solution and its correct final claim), near-miss mutants (9, all rejected) and accepted variants (alternative correct solutions). The control gate runs in CI.
- Hosts: Claude Code 2.1.301 (`-p`, project settings only, strict MCP config); Codex CLI 0.162.0-alpha.17.2 (`exec`, isolated `CODEX_HOME`).

### Evaluator defects found and fixed (not SotuRail's)

Applying the oracle-authority and accepted-variant lenses found five harness/oracle defects. Each was fixed, controls were extended, and affected runs were re-scored with the previous verdict kept in `oracleHistory`:

| Defect | Effect before fix | Fix |
|---|---|---|
| `node --test test/` fails on Node 24 | visible suites broken in every Node fixture | explicit glob |
| workspaces under a `soturail-qual` path | product name leaked into the baseline's cwd; `cd` counted as SotuRail calls | neutral `aq-runs` path; count only command invocations; first Claude pilot marked invalid |
| t11 rejected migration notes mentioning old option names | 3 correct Codex docs runs failed | reject only stale options presented as current; new mutant + positive control |
| JSON oracles rejected a UTF-8 BOM (PowerShell 5.1 default) | Codex baseline review counted as failed, crediting SotuRail with a review gain that did not exist | strip BOM per RFC 8259; `accepts/` controls |
| Python fixtures without `.gitignore` | `__pycache__` showed up as out-of-scope changes | realistic `.gitignore` |

Runs: `pilot-codex-002` (published 1.6.0), `candidate-codex-003` (fingerprint fix, `becfc0a`), `candidate-codex-004` (+ proportional skills, `e732c21`). Baseline values are from the same runs. Caveats, recorded in each run's `NOTE.md`: 003 and 004 ran with `CODEX_HOME` in the OS temp dir, where Codex runs without its helper binaries, so arm comparisons inside 003/004 are fair but 002 → 003 is confounded (the stale-evidence mechanism itself is verified by tests and dogfood, and 002's final messages name it explicitly); 004 hit the Codex plan usage limit on t09–t12, and those 12 runs are excluded as invalid.

Proportional skills reduced Codex's SotuRail calls by about a third and tokens by about a fifth on the valid tasks, with no loss of success. The SotuRail arms still cost about 2.2× the baseline for the same outcomes. This needs the full 12 tasks and 3 repetitions before it counts.

Remaining false-not-ready after the fingerprint fix is **policy-held**: for t03, t08 and t09 Codex created high-risk contracts, which require an independent review that an autonomous agent cannot provide, and reported NOT_READY with the reason. That is defensible governance, but it means a security fix done alone is never reported ready.

### Where the cost goes (Codex, 24 SotuRail-arm runs, published 1.6.0)

`soturail.read` via MCP 77 and via CLI 36 (replacing native file reads), `soturail run` 65, candidate records 34, evidence collect/verify 32, capability listing 17, contract create 11. The core skill told the agent to read every file through `project.read` and to record every finding as a candidate, with no proportionality rule.

Root cause of the readiness failure (verified): the workspace fingerprint digested the raw `git status` listing, which includes SotuRail's own raw logs, evidence and metrics when `.soturail/` is not gitignored — and `soturail init` does not gitignore it. Every recorded run therefore changed the fingerprint it had just been bound to. All existing test fixtures gitignored `.soturail/`, which masked the defect.

## 5. Remediation (Checkpoint 3)

| Commit | Change | Proof |
|---|---|---|
| `e5f1c15` | fingerprint excludes `.soturail/` runtime state; config stays bound via `configurationDigest` | 2 new regression tests (fail before the fix); dogfood 4/5 → 5/5; Codex stale false-not-ready 5 → 0 |
| `3bb0499` | guard reports `Path not found` and keeps `code: ENOENT` | regression test (fails before the fix) |
| `becfc0a` | `mcp config` adds a host-native, version-pinned `mcpServers` entry | unit test; live connection from Claude Code |
| `e3a99e7` | core/change skills scale ceremony to risk; `project.read` reserved for untrusted paths, secrets and large files; only durable findings recorded | Codex candidate run (section 3) |

Not changed, needs an owner decision:

1. **`soturail init` footprint.** It writes v0.4-era SotuRail documentation into the project's `docs/` and `examples/` (a tested public contract) and does not gitignore `.soturail/`. Recommendation: by default create only `.soturail/`, the agent entry files and a `.gitignore` entry; move the starter docs behind an opt-in flag with a deprecation notice. In 5 of 24 Claude SotuRail-arm runs the generated docs appeared in the agent's listings and once were read; no collateral edits were observed.
2. **High-risk contracts require independent review.** Agents that classify a security fix as high risk can never reach ready on their own. Either keep it (and document that autonomous security fixes end "policy-held") or let the human attestation path be suggested explicitly in the final report.

## 6. StructuralProvider readiness (Checkpoint 4)

Evidence from these runs:

- baseline agents located the code to change in 3–5 tool calls on average (max 10, Haiku); no oracle failure was caused by a missed dependent, call site or test;
- `structural.impact` is referenced by the change, debug and review skills and is `unavailable`; Codex compensated with hand-built impact candidates, which added cost without changing outcomes;
- the fixtures have 3–8 files, so this sample **cannot** show the value of structural facts — it only shows that small tasks do not need them.

Decision: **do not implement a StructuralProvider yet.** The smallest useful one, if a benchmark justifies it, is:

- deterministic facts only: reverse import graph for JS/TS/Python from import statements, test files that import a changed module, and Git co-change frequency for the touched files;
- bound to the workspace fingerprint like other evidence, with `unknown` for dynamic imports, re-export cycles and languages it does not parse;
- exposed as `structural.impact` with `availability: degraded` and the Semantic Worker still interpreting meaning;
- no graph database, no per-language semantic parsers, no new runtime dependency.

Gating benchmark (to build before any implementation): 3–4 tasks in a 50+ file fixture where the correct change must reach dependents the prompt does not mention — a signature change behind a re-export barrel, a renamed configuration key read from two languages, a review diff whose breaking effect lands outside the diff. Promote only if, with an experimental provider, regressions or missed dependents fall on ≥ 2 of 3 repetitions at no lower success.

## 8. Limitations

- Small hand-built sample; one repetition for most cells. Claims above are scoped to these tasks and hosts.
- Claude Code skipped SotuRail Skills almost always, so its arms test "installed but unused", not "used".
- Headless runs cannot measure interactive value (asking the user, reviewing artifacts).
- Codex cost is in tokens only; list-price comparison across hosts is not possible.
- Fixtures are Node/Python only; the Kotlin project could only exercise onboarding and error paths.
