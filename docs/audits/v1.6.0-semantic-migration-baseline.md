## 4. Implicit English dependencies (probed on `dist/` at baseline)

| Input | Observed | Consequence |
|---|---|---|
| `normalizeWords("Corrija a autenticação e verifique o impacto nos testes e rotas.")` | `corrija, autentica, verifique, impacto, nos, testes, rotas.` | Accents split words; `autenticação` → `autentica`. |
| `normalizeWords("認証の不具合を修正してください")` | `[]` | Japanese tasks produce **zero** tokens; every keyword ranking scores 0. |
| `keywordScore("Corrija a autenticação", "authentication login fix")` | `0` | Portuguese tasks never match English skill text. |
| `routeContext(pt-BR auth task)` | `code` via substring `test` in `testes` | Correct-looking result by accident, not by semantics. |
| `routeContext("Publicar la nueva versión en el registro")` | `code` (default) | Spanish release task is not routed to release. |
| `routeContext("リリースノートを公開する")` | `code` (default) | Japanese release task misrouted. |
| `slugifySkillName("認証レビュー")` | `skill` | Two Japanese-named skills collide on the same directory. |
| `slugifySkillName("Revisão de segurança")` | `revis-o-de-seguran-a` | Lossy, unreadable IDs. |

Other English assumptions: `rule-extractor` modal verbs (H06), Git message prefixes (H10), filler removal (H11), prompt-injection phrases (H22), skill/export headers written only in English (acceptable as human text; machine fields stay stable).

The fix is **not** a multilingual keyword table. Machine routing moves to the Semantic Worker; deterministic code only becomes Unicode-safe.

## 8. Migration plan

| CP | Slice | Key decisions |
|---|---|---|
| 1 | Canonical contracts | `capability-descriptor.ts` builds v2 descriptors **from** the v1 registry plus an additive v2 table; v1 `CAPABILITY_REGISTRY` and `capabilityRegistryDigest()` stay byte-identical. Planned capabilities carry `maturity: planned` and `availability: unavailable` instead of pretending to exist. `semantic-candidate.ts` defines candidate claim/impact/decision/question/interpretation schemas whose producer-assignable states are only `candidate`, `inferred`, `assumed`, `unknown`, `unverified`. |
| 2 | Portable core skill | Bundled skills live in a top-level `skills/` directory shipped in the npm package; `SKILL.md` frontmatter holds `name`/`description` (+ small `metadata`), a `soturail.skill.json` sidecar holds `uses` and trust metadata. Generic portable export writes directories, never flattens. |
| 3 | Task skills | change/debug/review/security/research/knowledge/release with trigger/non-trigger/composition fixtures (deterministic assertions on declared capability bindings and metadata, not keyword matches). |
| 4 | Discovery | thin projections of the descriptor: CLI `capabilities describe`, `skills discover/describe --level`, bounded read-only MCP tools/resources. |
| 5 | Host adapters | registry + golden fixtures; generic fallback for unverified hosts (Kimi and others) with explicit limitations. |
| 6 | Routing transition | keyword router labeled `heuristic-fallback`; agent-declared selection recorded; heuristic or model assertions cannot satisfy verification. |
| 7 | Multilingual | Unicode tokenization/slugs/identifiers; pt-BR, es, ja/Unicode-path and mixed-doc fixtures; `locale` + `statementOriginal` preservation. |
| 8 | Evidence | promotion only through recorded evidence; provenance on semantic/provider outputs; skill/capability usage linked to run artifacts. |
| 9 | Docs/migration | residual docs, migration guide, release notes draft. |
| 10 | Release qualification | full gates, then version/tag/release/npm. |

## 9. Migration risks

- **Capability epoch drift**: changing the v1 registry changes its digest and invalidates recorded epochs. Mitigation: v2 is a projection; v1 data unchanged unless a capability is genuinely added, which is then documented as intended drift.
- **Test coupling to English routing**: `tests/v050|v052|v061` pin English `routeContext` results. Mitigation: keep the fallback behavior and those tests; add separate tests that the primary path never consults it.
- **Package surface**: shipping `skills/` changes the npm `files` list; package dry-run must include it.
- **Host claims**: adapter paths for some hosts change quickly. Only hosts with current documentation and golden fixtures are marked verified; everything else is generic fallback.
- **Context bloat**: a skill catalog can cost more than it saves. Level-1 catalog bytes are measured and bounded by tests.
- **Self-promotion**: any new write surface for agent output must reject `verified`/`current`/`approved`/`ready` from the producer.
- **Docs scope check**: `code-health` scope-contamination terms apply to README/ROADMAP; vertical references stay in ecosystem docs.

## 10a. Trust gap found during CP6

`contract verify --check-passed <check>` accepts the caller's assertion as a passed check and hard-codes evidence freshness to `current`, so an agent can reach `ready` by asserting. CP8 builds the readiness snapshot from recorded run evidence and current fingerprints; asserted checks without evidence will not count.

## 10b. Contract lifecycle (CP10A)

The pre-v1.6 contract compared its creation fingerprint with the current one, so any implementation made it `workspace_stale` forever. CP10A separates the immutable baseline from verification freshness, adds lineage-preserving revisions, and classifies every caller flag as an unverified assertion. While testing it, a fingerprint bug was found: the first unstaged porcelain entry was misparsed, so re-editing an already-modified file did not change the fingerprint (fixed in `a3a9daa`).
